# State of the project, 2026-08-22

A review of where siberian-next stands after its first seventeen features, what
will hurt first as it grows, and what to change while the project is still
young enough to change cheaply. Facts were measured on the box, not recalled.

## Where it stands

Seventeen features shipped, all on `main`, all green: 98 lib tests, thirteen
smokes that drive the real stack, and a conventions check. The system does what
LOGBOOK.md says it does: modules in three languages install, get isolated data,
render framed in the shell, ship native screens into a per-domain phone app,
and are built into a real APK by a queued worker. The recurring bug class of
the past week was not logic errors but drift: state written once at install or
render time going stale against reality (menu conditionals, upstream maps,
service registrations, seeded roles, bind mounts, `lib/` loaded at boot).
Nearly every hard incident was a correct change colliding with another correct
change.

## Bottlenecks and issues, in the order they will bite

### 1. The box, before any software

The VM has 2 vCPUs and 7.8 GB, shared with a second project (stream-composer,
whose dataplane idles at 20 percent CPU), and a 47 GB disk that has filled
three times in one week. An Android build (Gradle plus Metro) competes with
Postgres, eleven Rails processes, and a live streaming stack for two cores.
Nothing in compose sets CPU or memory limits, so a build can starve the
databases that every request depends on. Housekeeping now keeps the disk
alive, but the ceiling is the hardware: this is the first real bottleneck and
it is not in the code.

### 2. Every byte transits every service, fully buffered

The media and artifact paths copy whole bodies through memory at each hop:

- A CMS image on a phone: Router, module (Python, full read), Router again on
  the core door, Storage (Rails, `object.body.read`), Garage. Four buffered
  copies per image view.
- An APK artifact: the builder reads 67 MB into memory, POSTs it to the
  Mobile service, which reads it whole (`request.body.read`), then PUTs it
  whole to Storage, which PUTs it to Garage. Three round trips of the same
  67 MB through Ruby strings.

At demo scale this is invisible. At ten modules and real media it is the
latency floor and the memory ceiling. The design cause is honest: modules must
not hold object-store credentials. The fix does not abandon that (see
proposals).

### 3. The reference modules teach an expensive pattern

`db()` in every reference module opens a new Postgres connection per request
and then runs `ensure_schema`, which is DDL (`CREATE TABLE IF NOT EXISTS`,
`ALTER TABLE`) on every page view. Auth is also asked over HTTP once per
module request with no cache (the core services cache identify for 30
seconds; the modules do not). The reference modules are the de facto SDK
documentation: third parties will copy exactly this. Fixing the pattern after
external modules exist means fixing it in code nobody controls.

### 4. Drift has no general answer yet

`RouteReconciler` converges routing, and it has already paid for itself
twice. But it is the only reconciler. Service registrations (a module
installed before the Mobile service existed is invisible to it), seeded roles
(a permission added after seeding reaches nobody), the Router upstream map
(fixed by hand once), and hosts entries all share the same shape: derived
state written once, never re-derived. Each got a one-off fix or a candidates
entry. The class keeps producing incidents because the system installs
imperatively rather than converging on desired state.

### 5. One flat admin token

Every core service authenticates every other with the same static bearer
(`SIBERIAN_ADMIN_TOKEN`). Compromise of any one service is admin on all of
them: Storage could mint database credentials, the Mailer could delete
buckets. The builder already demonstrates the better pattern (its own token,
scoped endpoints, no Storage credential). The flat token is fine for a dev
box and wrong for the first real deployment, and retrofitting per-service
credentials later touches every service at once.

### 6. The stack runs Rails in development mode

`RAILS_ENV=development` on the box means per-request code reloading, no eager
loading, and verbose logging in every core service. Eager loading in
production mode would have surfaced the stale-`lib/` NameError at boot
instead of as a 500 on the third page somebody opened. It also makes every
measured latency a lie relative to what production would do.

### 7. Single instances everywhere, only some of which matter

One Router, one Garage node, one core Postgres cluster, one module-data
cluster, one builder. For this stage all are acceptable, but they are not
equal: the Router and the two Postgres clusters are in the request path of
everything, while the builder and Garage only gate background work. Worth
writing down so nobody spends effort making the builder redundant before the
Router.

### 8. CI cannot catch the bugs this project actually has

CI runs the lib suite and per-service Rails tests. Every incident this week
(drift, headers, mounts, caches) lived in the seams between services, which
is exactly what the thirteen smokes cover, and the smokes only run when
somebody runs them on the box. The gap is structural: the smokes need a real
engine, real TLS, and eleven containers. Until they run somewhere automatic,
`main` is only as green as the last person who remembered.

## Proposed next major changes

Ordered by leverage per unit of disruption, highest first.

### A. Make reconciliation the installation model

One `Reconciler` that converges all derived state: routes, the upstream map,
service registrations (each core service exposes what it knows, the
Orchestrator re-registers what is missing), role catalogue additions (new
permissions append to seeded roles that have not diverged on that
permission), and the hosts inventory. Run it at boot, after install, and from
a Backoffice button, exactly as Repair routing works today. Install becomes
"write desired state, converge", and the whole drift bug class collapses into
one place with one test. This is the highest-leverage change available, and
it is cheap precisely because only five modules and seven services exist.

### B. Move bytes out of the request path

Storage learns to mint short-lived signed URLs (Garage speaks S3, presigning
is free) and the Router gets the already-planned `/-/public/<path>` rule.
Uploads: a module asks Storage for an upload URL and hands it to the browser.
Downloads: public media is served by the Router straight from Garage, private
media by redirect to a signed URL. Modules still never hold a credential,
which preserves the audit property; they hold a URL that expires. Do it now
because it changes the module contract (media URLs), and the only modules
that exist are the reference ones.

### C. Turn the reference patterns into the first SDK

Fix the reference modules (connection pool, schema at boot, a 30-second
identify cache), then extract exactly that into the promised Python SDK, and
port demo-tasks to it. The SDK is not a convenience layer here, it is how the
correct patterns propagate: LOGBOOK.md already promises SDKs, and the
cheapest moment to define one is before anyone external writes a module
without it.

### D. Split trust: one credential per service pair

Replace the shared admin token with per-service tokens issued the way module
tokens already are (the pattern exists in three services). The Mobile
service's builder token proves the shape works. Do it before the first
non-development deployment, because afterwards it is a coordinated rotation
across every service at once.

### E. Run the box like the smallest production

`RAILS_ENV=production` with eager loading (boot-time NameErrors instead of
runtime 500s), compose resource limits so a Gradle build cannot starve
Postgres, and either a second VM for the builder or an agreement that builds
are the sacrificial workload. Separately: the box needs more than 2 vCPUs if
it keeps both projects.

### F. A nightly smoke run on the box

Cron already runs housekeeping. Add the smoke sweep after it, writing one
line per smoke to a log the Backoffice overview shows next to CoreHealth.
That is alerting and CI-for-the-seams in one cheap move, and it uses only
what already exists.

### Explicitly not proposed yet

Kubernetes (the driver boundary already isolates the decision), multi-node
Garage, module marketplace mechanics, and OAuth. Each is real and none is the
current constraint.
