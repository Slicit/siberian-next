# Converging derived state, instead of writing it once

## Intent

The recurring bug class in this project is not logic errors, it is drift: state
written once at install time and never re-derived, going stale against a system
that moved. The review on 2026-08-22 counted the instances, and they are all
the same shape:

- A module installed before the Mobile service existed is absent from every
  phone app, because only install tells Mobile a module exists. `example-notes`
  and `example-relay` are in that state right now.
- A permission added to the catalogue never reaches an already-seeded role.
  `core.storage.manage` shipped and no seeded operator role held it.
- The Router upstream map went stale and was fixed by hand once.
- Replacing the Router loses its network attachments, and every module route
  answers 502.

Only the last one has an answer: `RouteReconciler`, which has already paid for
itself twice. This feature generalises it. One `Reconciler` runs ordered,
idempotent steps that compare what the database says should be true against
what each service actually knows, and closes the gap.

The point is not the three bugs above. It is that the next piece of derived
state gets a step here instead of a fresh incident.

Out of scope for this feature:

- The hosts file. It is a development convenience generated by `bin/hosts-file`,
  not state a running system depends on.
- Rotating a token that is already working. See the decision below: that is the
  difference between a reconciler that is safe to run at any time and one that
  is not.

## Plan

1. Each service answers what it knows. `GET /admin/modules` on Storage,
   Database, Mailer, and Mobile, returning registered module names and no
   secrets.
2. `Reconciler` in the Orchestrator: ordered steps, per-step results, one
   `Activity` record.
3. Step: routes. Delegates to `RouteReconciler` rather than reimplementing it.
4. Step: mobile registrations. Re-registers every live module, because the
   Mobile token is issued and never used, so re-registering costs nothing.
5. Step: token-bearing registrations. Reports a module the Storage, Database,
   or Mailer service has never heard of, and does not fix it silently.
6. Step: roles. A permission added to the catalogue reaches seeded roles that
   have not diverged on it.
7. The Backoffice runs it, and the Overview shows what it found.
8. `bin/smoke-reconcile` drives the real thing.

## Decisions

### 2026-08-22: the reconciler repairs what is free and reports what is not

Re-registering a module with Storage, Database, or Mailer issues a new token
and stores its digest, which makes the token already in the running container's
environment authenticate against nothing. The module keeps running and every
call it makes to that service starts failing. Reconciling that way would take a
system with one stale registration and break three working ones, which is worse
than the drift it set out to fix.

So the steps are split by what they cost:

- Mobile registration is re-sent unconditionally. `register_mobile` returns a
  token that `ModuleInstaller` never injects into anything (only the storage,
  database, and mail tokens reach a container), so rotating it has no effect on
  any running module. This is the step that fixes the known bug.
- Storage, Database, and Mailer registrations are compared and reported. A
  module the service has never heard of is named in the result and in the
  Activity trail, with the repair being a module reinstall, which recreates the
  container with the new token in it.

A reconciler that is unsafe to run at any moment does not get run, and then it
is not a reconciler. Reporting the expensive half keeps the cheap half
runnable on a button.

### 2026-08-22: role drift is measured against the catalogue as it was last seeded

`seed_defaults!` skips a role that already exists, which is what stops it
overwriting an operator's edits, and also what stops a new permission ever
reaching an existing installation.

Re-seeding wholesale would overwrite the edits. Adding every catalogue
permission the role lacks would re-add exactly the ones an operator removed on
purpose. Neither is right, and the missing information is the same in both: what
the catalogue said the last time this role was seeded.

So roles record it, in `seeded_permissions`. Reconciling adds the difference
between the catalogue now and the catalogue then, which is precisely the
permissions that did not exist when the operator last had an opinion, and
leaves everything else alone. An operator's removal survives, because the
removed permission is in the previous snapshot and so is never in the
difference.

### 2026-08-22: found the test double had been broken for eight days

The first run of the new tests failed for a reason that had nothing to do with
them: `FakeRouter` never grew `refresh_upstreams!` when `ModuleInstaller`
started calling it, so every orchestrator test that installs a module has been
failing on `main`, and the GitHub Actions run has been red on every push since
2026-08-20.

Seven failures, fixed by four lines in the double. Worth recording not for the
fix but for what it says about the review's last point: nothing that runs
automatically was watching, and the smokes that would have caught the same
class of thing only run when somebody remembers to run them.

## Outcome

Shipped. Both drift bugs the review named are closed on the box, verified
against the services' own state rather than the Backoffice's opinion of it:

- `example-notes` and `example-relay` were absent from the Mobile service since
  the day they were installed. The Mobile service's inventory and the
  Orchestrator's now list the same five modules.
- The operator role was missing `core.storage.manage` and `core.mobile.manage`,
  both added to the catalogue after the role was seeded. It holds both.

What runs: `Reconciler` behind a Backoffice button, four steps, one Activity
record. Twelve tests on the reconciler, eight on the role logic, and
`bin/smoke-reconcile`, which makes the Mobile service forget a module and
checks that reconciling brings it back, then that reconciling again changes
nothing.

Left undone deliberately: nothing calls the reconciler automatically. It is a
button and a smoke. Running it on a schedule belongs with the nightly smoke
sweep, which is its own piece of work.
